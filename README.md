# Textcrew landing page

Marketing site for Textcrew, the personal AI agent you text from Telegram or the web app. It is in **private beta, launching soon**, so the page's job is to explain the product and collect beta waitlist signups.

Built with Next.js 16 (App Router, Turbopack), React 19, Tailwind CSS 4, three.js (3D hero), motion (scroll reveals) and simple-icons (app logos). Waitlist signups are stored in Neon Postgres through Drizzle ORM. Package manager: pnpm.

## Run it

```bash
pnpm install
cp .env.example .env.local   # then paste your Neon DATABASE_URL
pnpm db:migrate              # creates or updates the waitlist_signups table
pnpm dev                     # http://localhost:3000
```

Other scripts: `pnpm build`, `pnpm start`, `pnpm lint`, `pnpm db:generate` (new migration after a schema change), `pnpm db:studio` (browse signups).

## Environment

| Variable | Needed | What it does |
|---|---|---|
| `DATABASE_URL` | Yes, for the waitlist | Neon Postgres connection string (use the pooled one). Without it the waitlist API answers `503` and nothing is stored. |
| `RESEND_API_KEY` | Production | Sends the waitlist confirmation emails through [Resend](https://resend.com). In development without it, the confirmation link is printed in the server log. In production without it, signups get an error and no email is sent. |
| `WAITLIST_FROM_EMAIL` | Production | Sender for those emails, on a domain verified in Resend. Defaults to `Textcrew <no-reply@textcrew.in>`. |
| `NEXT_PUBLIC_SITE_URL` | Production | Canonical URL for metadata, sitemap and social cards, and the base of the confirmation link. Defaults to `https://textcrew.in`. |

On Vercel, add these in the project's environment variables (the Neon integration can set `DATABASE_URL` for you).

## Beta waitlist

`POST /api/waitlist` validates the email, ignores bots that fill the hidden honeypot field, allows at most 5 new signups per IP every 10 minutes (checked in the database, so it holds across serverless instances), then upserts one row per email into `waitlist_signups`.

Each row stores:

- email and preferred chat app (optional)
- IP address, user agent, `Accept-Language`, browser language, time zone and screen size
- approximate location from Vercel's IP headers: country, region, city, latitude and longitude (Cloudflare's country header works too)
- referrer, landing page and UTM tags (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`)
- `created_at`, `last_seen_at` and `signup_count`; repeat signups only bump the last two and keep the first-touch details
- confirmation: `verified_at`, `verified_ip`, and the pending link's token hash, expiry and send count

**Email confirmation (double opt-in).** A signup only counts once the email is confirmed (`verified_at` is set), so count and export only confirmed rows.

1. After saving the row, the route emails a confirmation link, `/waitlist/confirm?token=…`, valid for 48 hours, from `no-reply@textcrew.in`. Only a SHA-256 hash of the token is stored, and a new email replaces the previous link. An already-confirmed address gets no email at all.
2. The confirm page checks the token only when the visitor presses **Confirm** (a server action), so mail-app link scanners can't confirm an address by opening the link. It records `verified_at` and `verified_ip`.
3. Signing up again sends a new link at most every 30 minutes, and three a day. The form tells people that if they're already on the waitlist, no email comes.

New, pending and confirmed emails all get the same response, so nobody can check who is on the list. The `/privacy#waitlist` section tells visitors what is stored; keep it in sync with the schema in `src/db/schema.ts`. The SQL lives in `drizzle/` if you'd rather run it in the Neon console.

## SEO and analytics

- `src/lib/site.ts` holds the search title, description (kept under 160 characters) and keywords. Social cards use the tagline and `opengraph-image.tsx`.
- Each page sets its own canonical URL. The homepage adds schema.org JSON-LD: Organization, WebSite, SoftwareApplication (with the plans) and FAQPage, built from `content.ts`.
- `robots.ts` blocks `/api/` and `/waitlist/`; `sitemap.ts`, `manifest.ts` and `apple-icon.png` are generated by Next.
- Vercel Web Analytics (`<Analytics />` in the layout) counts page views and referrers without cookies; the privacy page says so under "When you visit the site".
- `NEXT_PUBLIC_SITE_URL` must be the site's final address (the one that doesn't redirect), because canonical links, the sitemap and email links are built from it.

## What's on the page

Sections, in order: a centred hero with the waitlist form and floating app logos; a product window (chat with a working approval card, plus Activity, Approvals and Automations tabs) with the 3D Tex perched on top, calling crew members in; how it works (the job told through lock-screen notifications from Tex, with a working Approve); integrations (a job receipt that prints each app action and its credits while an app shelf lights up); use cases; an automations builder; the crew (an auto-playing story of Tex handing work to the specialists) and roadmap; privacy and security; features; a short pricing teaser that links to `/pricing`; FAQ; and a final waitlist call to action.

Other pages: `/pricing` (the plans, the waitlist deal, how credits work, a line on dollars, tax, Polar as merchant of record and cancelling, the FAQ questions about plans and credits, and the waitlist form) and a `/privacy` summary, with a section on data from Google apps (`/privacy#google-data`, Google's "Limited Use" statement), one on payments through Polar (`/privacy#payments`) and a contact line (`/privacy#contact`). The contact email is `site.contactEmail` in `src/lib/site.ts`, shown in the footer, on Pricing and on Privacy; change it there only. The nav and footer link home sections as `/#id`, so they work from every page. The FAQ questions marked `pricing: true` in `content.ts` are the ones `/pricing` repeats.

The visual language follows the products it sits next to (Notis, Multiply, Strawberry): light background, centred sections, real app logos, product mockups and pill buttons.

Section copy lives in `src/lib/content.ts` and `src/lib/site.ts`, taken from the platform overview and the backend HLD (plans, credits, security, roadmap). Change wording there, not in the components. The scripted demos (product window, how it works, integrations, automations builder, crew story) keep their lines next to the animation in their own component.

## Notes

- **Mascots.** Tex is the captain, available at launch; Byte (coding), Patch (code review) and Scout (research) are shown as "soon": they arrive with or soon after launch. 3D is used only in the hero; everything else is 2D.
- **3D fallback.** The hero shows the 2D Tex until three.js has loaded, and keeps it if WebGL isn't available. Rendering pauses when the stage is off-screen or the tab is hidden.
- **Motion.** All animation respects `prefers-reduced-motion`.
- **Theme.** Light only, on purpose, to match the category.
- **No analytics or cookies** yet, so no cookie banner is needed. Add one if you add analytics.
